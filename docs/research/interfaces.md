# Interfaces

The core finding: **the interface debate is a proxy war over loading policy** (GLMC Pattern 1). Every "CLI beats MCP" or "Code Mode beats both" result traces to the same mechanism — how much schema and instruction text enters context per turn — not to the transport. The MCP spec (2025-06-18) itself delegates tool exposure to client policy; `tools/list` supports pagination and change notifications (GLMC Finding 3). Optimize **what enters context**; treat the interface as a thin adapter.

Two cost centers, routinely conflated, tracked separately throughout (GLMP §2, DSV §0):

- **Schema rent** — fixed per-turn cost of tool definitions loaded every call; grows with conversation length.
- **Response bloat** — per-call cost of oversized tool outputs flowing through context.

Corroborating practitioner figures (secondary, unverified units — DSV §3): ~55k tokens ≈ $0.16/session ≈ $1,600/day at 10k sessions (Chawla — an earlier config that predates the GitHub MCP slim-down per DSV §5, not comparable to the 44/85-tool rows); Perplexity CTO: MCP descriptions = 72% of context before work; one Claude Code user: 34k → 80k tokens from registering GitHub MCP (GLMP); a community comparison measured **32% of context with the GitHub MCP server enabled vs 8% without**, top reply recommending `gh` (GLMP); Simon Willison's widely cited measurement: the GitHub MCP server defines **93 tools ≈ 55,000 tokens** before any work begins (DS §3); a similar practitioner figure from HN puts the GitHub MCP spec load at ~54k tokens (KIMI §5); GitHub's own `cli-proxy` work reports GitHub MCP injecting roughly **22 tool definitions, ~10–15K tokens** into every turn (DS §3); a typical 4-server MCP setup costs ~7k tokens/message in tool definitions (gateway-vendor measurement, KIMI §5); and GLMP §4 relays the MCP-spec proposal discussion #2812's measurement of **eleven production tools at ~10,000 tokens — "roughly five pages of reasoning capacity permanently unavailable to the model for the whole session."** An HN commenter's summary of where the field landed: "Both Claude and OpenAI solved the MCP context-bloat issue with on-demand tool discovery" (GLMC Finding 3).

Community counter-anecdotes (flagged tier — uncontrolled, DSV §2–3): an enterprise-IT writeup reports a ~35× token ratio for an Intune device-export task with no model/repetitions/tokenizer/correctness disclosed (GLMC: uncontrolled anecdote); the OnlyCLI "35×" post concedes mixed provenance (independent benchmarks + own measurements, 93-tool server assumed); a Chinese-dev-community Bilibili post reports "~6× average token savings" switching an agent from MCP to the `hf` CLI — search-derived, un-linked, treat as unverified anecdote, with an adjacent alternative framing ("Exa-code: 1B+ GitHub + Stack Overflow to reduce hallucinations" positioned against Context7).

**Why a single tool costs 200–500 tokens** (GLMP §4): name + prose description + full JSON Schema with types, descriptions, and recursive enums — most tokens tell the model what a string is. Raw MCP servers that dump dozens of tool schemas cost in a **17,600–80,000-token band** before the agent reads its first message (GLMP §1), extrapolating to ~75,000 for ten servers (GLMP §4). Atlassian's compression proxy measured GitHub's 17.6k schema falling to 3,900 (enum/type dedup, full descriptions kept) → 3,300 (first sentences) → 2,200 (bare parameter names) → 500 (single `list_tools`). **Catch: below the summary level, compression trades accuracy for tokens** — the model can't disambiguate similar verbs. GEM §4's band for a single MCP tool definition (schema + descriptions) is 550–1,400 tokens; at that rate, enterprise SaaS connectors exposing 50+ endpoints reach 50,000–143,000 tokens — up to 72% of a 200k window before any work begins (corroborates the ~143,000 row above). At the opposite end, a specialized 1–2-tool docs surface costs only **600–1,200 tokens of upfront MCP schema — virtually identical to an 800-token CLI SKILL.md** (GEM §4): at docs width the interface choice is near-moot on schema rent, which is why payload design and retrieval quality decide.

**Response bloat at 2-tool width (Ref vs Context7, GEM §2).** Both expose ~2 tools (~500–800 schema tokens), yet Context7's default payload is 5,000–10,000 tokens/lookup vs Ref's ~500–5,000: session-trajectory dedup (never re-return served URLs/chunks) plus section dropout scored against the session's search history averages **5,500 tokens saved per request** (up to 95% vs Context7, ≈$0.082/request at Opus pricing). At two-tool width the differentiator is payload design, not transport — see the session-dedup contract in [retrieval-design.md](retrieval-design.md). Ref's implementation is a commercial SaaS ($4M seed, per-seat/usage pricing): multi-tenant vector namespaces in Turbopuffer, metadata in Firestore, isolated Cloud Run containers; `ref_read_url` returns ~500-token targeted excerpts and caps full-URL reads at 5,000 tokens where naive scraping would yield 20,000+ (GEM §2); its two tools are deliberately mapped to search and fetch for OpenAI deep-research compatibility (GEM §2).

**Accuracy side of the tax.** RAG-MCP (arXiv:2505.03275): tool-selection accuracy 43.13% with retrieval pre-selection vs 13.62% raw large catalog (~3×, 4,400-server registry; one non-frontier model; precision degrades past ~100 candidates — GLMC Finding 4). Anthropic guidance: selection degrades past **30–50 concurrently-loaded tools**; Claude Code schema cost ~10–20k tokens per 50 tools (GLMP). Cursor caps servers at 40 tools from telemetry (GLMP). Claude Code auto-defers tool descriptions exceeding ~10% of context (GLMP). GitHub's own maintainers consolidated 9 issue tools into 3 and cut response tokens 60–92% via structured JSON (GLMP) — the flagship server spent 2025–2026 shrinking itself. GEM §4 names the mechanisms: `structuredContent` fields or compact Markdown over raw dumps, and `since_last` terminal-output diffing (60–92% per-call cut; 39% cost reduction on complex output-heavy tasks even against deeply pre-trained tools like tmux, per Dave-London's Pare evaluations on GitHub issue #1286).

**MCP vs CLI, the controlled benchmark (Scalekit, March 2026) — and its audit.** Identical tasks through CLI (bare bash), CLI+Skills (~800-token tips file), and GitHub MCP (43 schemas), Claude Sonnet 4, five read-only GitHub tasks. 75 runs total. Published medians: 1,365 vs 4,724 vs 44,026 tokens (CLI / CLI+Skills / MCP) on the simplest task (**32×**); 4–32× across tasks; CLI hit 100% task reliability (25/25) vs 72% for remote MCP (7 TCP ConnectTimeout failures; CLI local: none), and the ~800-token skill cut CLI latency and call count ~33% while *adding* tokens on trivial lookups (reliability, skill-median, and 33% figures: GEM §4). GLMC audited the open result pack at pinned commit `f131dd8`:

- Token medians reproduce exactly (recomputed ratios 32.3, 19.6, 8.8, 6.7, 4.3). Per-task published medians (CLI / MCP tokens, ratio): 1,648/32,279 (20×), 9,386/82,835 (9×), 5,010/33,712 (7×), 8,750/37,402 (4×) (GPT1/GPT2 §4.2).
- **But**: `task_completed` = "produced any final text," not a verifier verdict; the delivered study abandoned its own pre-registration (30 runs/cell → n=3–5 MCP; Wilcoxon registered, Mann-Whitney delivered); the dollar extrapolation is off 16–107× vs its own data.
- Audit micro-detail (GLMC Finding 2): the result pack holds **68 stored result files (25 CLI, 25 CLI+Skills, 18 MCP) against 75 scheduled runs** — the 7 failed MCP runs are absent from `results/raw`, so failure-rate analysis rests on the blog's account, not stored records; all 68 stored runs show `task_completed=true` (transport success, not answer correctness); for four of five tasks every stored run passed a **`contains` check**, while Task 4 is LLM-judged with **no judge verdicts in the public pack** — so the "100% vs 72% reliability" headline is mostly a network-topology statement; and the audit understated one defect — the CI code **silently truncates the larger group by zipping the arrays**, so the delivered interval and test are not even internally consistent.
- Dollar reproduction (GLMC Finding 2): at the blog's stated uncached pricing, its token medians imply **$0.005–$0.034 per CLI run and $0.10–$0.25 per MCP run** — $51–$342 vs $1,005–$2,537 per 10,000 runs; the published "$3.20 vs $55.20" is **16–107× lower (CLI) and 18–46× lower (MCP)** than its own data and pricing imply. Most plausible unaccounted factor: prompt caching, which the blog never mentions.
- **CLI+Skills crossover numbers** (GLMC Finding 2): the ~800-token skill file **raised** cost on the simple task (1,365 → 4,724) and **lowered** it on the most complex (8,750 → 6,860) — the mixed result that motivates the skill-size open question in [verdict.md](verdict.md).
- Mechanism is solid: **cost dominated by 43 schemas injected every turn, of which the agent uses one or two**. Indicts *large static catalogs*, not MCP. A 2–4-tool docs server's static schema cost is a few hundred tokens — the debate is nearly moot at that width (GLMC Insight 1). Lunar.dev's widely shared rebuttal states the same mechanism: the CLI-vs-MCP gap "is a comparison of 1 tool in context vs 43. Load 43 CLI tool definitions into the system prompt and you get the same overhead. The 30× gap is a property of naive tool loading, not of MCP" (GLMC Finding 3). Even GitHub's own filtered catalogs carry more scaffolding than practitioners want — issue #1683 asks for the CLI's properties: less verbose prompts and repository-context focus "similar to how `gh` CLI operates" (GLMC Finding 3).
- Caching: these are *uncached* figures; the only caching-aware benchmark found 2–3×, not 4–32× (GLMC Finding 2). Read uncached ratios as an upper bound.
- The audit's own limits (GLMC Gap 5): a single-repository, single-commit, single-timepoint recomputation by one team — no independent party has re-run it; the recomputed ratios carry no confidence intervals (point estimates from stored medians); the p-value pipeline was not re-executed end-to-end; the cost extrapolation is uncached and uses an arbitrary 10,000-run multiplier; and "pre-registered" is presumed from a same-commit methodology file, not proven by timestamps.
- Dollar normalization: raw token counts hide cache discounts and output asymmetry. GitHub Copilot engineering's **Effective Tokens** metric (Cox & Kiefer, May 2026, production CI/CD workflows — GEM §4) normalizes: `ET = m × (1.0·I + 0.1·C + 4.0·O)` — model multiplier m (Haiku 0.25×, Sonnet 1.0×, Opus 5.0×), uncached input at 1.0×, cache-read at 0.1×, output at 4–5×. A 10% ET reduction is a real 10% cost reduction on any tier. On this metric Scalekit's 10k-ops/month case is $3.20 (CLI) vs $55.20 (MCP), 17× (GEM §4).
- **Cost model: dollars per 1,000 agent queries (GLMP Ch.9).** Modeled monthly LLM spend of 1,000 documentation queries under four architectures, at frontier list pricing ($3/M in, $15/M out; efficient class $1/$5; output priced at full rate in all rows): **$3.66 / $1.66 / $0.34 / $0.15 per 1,000 queries for raw MCP / hosted API / code mode / CLI+local (frontier class) — a 24-fold spread** driven almost entirely by schema rent and response size, not model choice. Assumptions per query (GLMP Table 6): raw MCP = 26,000-token schema rent amortized over a 10-query session (2,600 input/query) + 500 in / 1,500 out per call; hosted API = 1,500 schema + 4,000-token response + 300 output, with its $5-per-1,000-call overage reported separately; code mode = 1,500 schema + 500 in / 400 out after sandbox filtering; CLI+local = zero schema, 800 in / 400 out, plus amortized ingest ($0 with BM25-only, ~$0.02/1M tokens with economy API embeddings). Two crossover findings: the hosted API's $5/1k-call overage **exceeds its own token cost at efficient-class rates** — fees, not tokens, dominate hosted-API economics at volume (the quantitative echo of the January 2026 free-tier cut); and raw MCP is the only row that worsens with shorter sessions — at 3 queries/session its rent nearly triples, to roughly **$12.20 per 1,000 queries**, precisely the profile of a quick IDE question. Sensitivity: halving response sizes cuts hosted/raw-MCP rows 35–45% but cannot close the gap (the remainder sits in definitions and fees); the ranking is invariant to model class — moving all queries to the efficient class **multiplies every row by exactly one third** (GLMP Ch.9); under Enterprise custom pricing the ranking can flip for high-volume users — the one scenario where a hosted contract beats code mode, though CLI+local remains cheapest. All figures are **modeled estimates under stated assumptions, not invoices** — but the ranking is robust across every parameterization tested within the measured token bands (GLMP Ch.9–10). This is the model behind architecture.md's ≤$0.20/query Phase-3 gate; the schema-rent measurement it depends on is exactly what that gate reproduces first.
- Production corroboration: GitHub's own team found the full GitHub MCP at 66–93 tools adds 46–55k upfront tokens; pruning unused tools saved several thousand tokens per run (−8 to −12 KB per call) and replacing MCP data-fetching with pre-agentic `gh` JSON reads eliminated tool-call round-trips for deterministic operations; their CI/CD agentic loops cap at 50 turns (GEM §4).

**Zechner's same-tool benchmark** (terminal-control tasks, not docs): MCP vs CLI ~100% success both arms — GEM §4 states the experiment shape (3 tasks, 120 runs total ≈ 30 per arm across four arms, tmux the $22.00 third arm), consistent with GLMP's 10 runs/arm/task, though DSV still flags the per-arm denominator as unverified; his 30-run dollar/time totals are **$19.45 (MCP) vs $19.95 (CLI), 51 vs 66 minutes** (GEM §4); aggregates conflict across sources ("MCP 23% faster, 2.5% cheaper" vs "MCP most expensive of four") — the full per-arm table and reconciliation live in [verdict.md](verdict.md). His CLI preference is stated judgment: *"make a good CLI... adding an MCP server on top of it is very straightforward."* Notable anomaly: CLI calls triggering the host's malicious-command detection consumed 1.3–2M safety-scan tokens vs ~35k for MCP equivalents (DSV §3). GEM §4 supplies the mechanism: Claude Code dispatches a background claude-3-5-haiku check on every Bash invocation — 1.3M–2.0M Haiku tokens and ~15 minutes across 30 runs (66 min total vs 51 for the 1-tool MCP, which bypasses the check); harness allowlisting of the exact CLI pattern (`Bash(docctl:*)`) bypasses the tax.

**The counterweight: scaffolding can dominate the interface (DS §3).** But this is not a universal law. A controlled comparison across **seven agent scaffoldings and five models** found that **scaffolding matters more than the interface**: paired MCP-to-CLI cost ratios ranged from **0.43× to 29×**, and two scaffoldings without MCP support completed all runs using only the CLI while being **5×–28× cheaper** than MCP-supporting scaffoldings. A separate **50-task study** found CLI helps less capable models on retrieval-heavy tasks but is neutral or worse on lighter tasks, and frontier models perform similarly across interfaces (DS §3). These are among the only multi-model controlled comparisons in the corpus and the direct evidence behind the eager-vs-lazy reframe — "CLI beats MCP" is not a protocol result. Independently, a separate practitioner benchmark of GitHub operations (kunchenguid — published with an HN discussion, caching accounted for) found GitHub MCP 2–3× more expensive than CLI with a **12× gap on a multi-step CI-failure investigation**, and ends by recommending "none of the above" for GitHub operations — a recommendation that does not transfer to docs lookup, where "none" means trusting exactly the training-data knowledge the tool exists to correct (figures: GLMC Finding 2; "none of the above" recommendation and non-transfer argument: GLMC Finding 3 Implications).

A third-party **browser-automation CLI-vs-MCP benchmark** (cited by CircleCI — KIMI §3) measured +33% token efficiency and a 77 vs 60 task-completion score for CLI vs MCP, with the gap largest in multi-step debugging, where MCP ran out of context mid-task. Adjacent-domain (browser tools, not docs) and secondhand — directional only.

## 2. Where MCP genuinely wins

Real advantages, not vendor spin (GLMC Finding 3, DS §3, GPT2 §6.1):

- **No shell in the harness** — the deciding factor; structured tool calls for GUI/remote clients.
- **Credential custody / audit** — an *implementation and deployment* property, not protocol-guaranteed: server-side facade holding credentials, or CLI + host-managed credential helper; choose by required audit controls.
- **Remote transport + typed I/O** for governed multi-user services (identity, tenant isolation, quotas — all deployment controls, see [security-licensing.md](security-licensing.md)).
- MCP failures can be *silent* where CLI failures are explicit (exit code + stderr) (KIMI §3); conversely MCP keeps host shell safety-heuristics untriggered (GEM §4).
- **Stateful operations — a capability, not a default** (DSV §3): a server *can* maintain session state, but nothing in the protocol makes it automatic — statefulness is an implementation/deployment property, and a CLI can hold state too (files, a daemon, a scratch dir). Zechner's nuance points the same way: MCP servers remain the right choice where stateful operations are "easier to implement as MCPs since MCP servers are stateful by default" (GLMP Table 4).

CLI costs usually left unstated (GLMC Finding 3): the harness still pays for a shell tool definition; a **novel** docs CLI has no model prior knowledge, so a skill/instruction file is mandatory (Context7's own CLI skill pack ≈ 9.9 KB); CLI+Skills mixed result (added cost on simple tasks, lowered on complex); verbosity tax unless output is bounded by design.

**Eager vs lazy, not MCP vs CLI** (DSV §3, explicitly the report's own synthesis): a bloated MCP and a sprawling `--help` tree fail the same way (too much disclosed up front); a lean MCP and CLI+skill share the same low-overhead property. Whether success is *equivalent* across MCP and CLI is untested — no common benchmark exists.

## 3. Code Mode (code-as-action)

**Pattern**: tool surface materialized as typed code stubs; the agent writes code in a sandbox; intermediate results never round-trip through the model; only final output returns. Two token drains fixed: eager definitions and intermediate-result flow-through. Also enables in-sandbox filtering (fetch 10,000 rows, show 5) — response bloat paid at the answer, not the payload (Anthropic; GLMP §5, DS §2). Mechanics (GEM §3, Cloudflare Agents SDK): fetched JSON tool schemas are transpiled into compact TypeScript interfaces (JSDoc lifted from the schema descriptions) exposed under a global `codemode` object; agent-written TypeScript executes in Workers V8 isolates or local equivalents (Deno, QuickJS) spawned per snippet in milliseconds; `fetch()`/`connect()` are disabled and throw, while `codemode.*` calls route over typed in-memory RPC (`ctx.exports`) to the host that holds credentials — prompt-injected sandbox code cannot exfiltrate secrets or reach the network.

Measured (each vs its own baseline — not comparable):

**Thresholds that bound the pattern** (GLMC Finding 4): schemas are 60–80% of static-toolset tokens (Speakeasy) so lazy loading is the whole game at scale; savings are negligible **below ~10 tools** (Anthropic: "10 to 49 tool definitions see typical token savings of 20 to 40 percent"); discovery machinery pays only near the **30–50-tool degradation point**. CodeAct (ICML 2024, 17 LLMs): code wins on *multi-step composition* (up to +20% success, −30% actions; M3ToolEval with GPT-4-0613: 67.1 CodeAct vs 56.1 JSON vs 45.1 text) but **closed-source models favored JSON on atomic calls** (GPT-4: 82.0 JSON vs 75.4 CodeAct) — the advantage is composition, not per-call quality (GLMC Finding 4). On the Stripe bench's complex multi-step task the composition advantage is stark: CLI 19 turns (497,556 tokens), raw MCP 12 (168,480), code mode 4 (38,847) — 12.8× vs CLI, 4.3× vs raw MCP (GEM §3).

**Other points on the dynamic-discovery curve**: MCP-Zero reports 98% token reduction on APIBank while selecting among **2,797 tools across 308 servers** — a single-paper result with no independent replication, cited as an upper-bound illustration, not a calibrated anchor (GLMC Finding 4). FastMCP's own documentation is candid about the core trade-off — **tokens vs round-trips**: more discovery steps mean less wasted context but more latency and API calls; fewer steps mean more upfront detail and more wasted context (DS §2). Open-source local code mode exists too (portofcontext / `pctx`, Deno sandboxes): its thread reports agents handling roughly **60–80 tools before degradation**, and the recurring plaint — "47 tools = 141k tokens consumed before you write a single word" (DSV §2).

**Where code mode underperforms** (GLMP §5): latency inversion on single lookups (seconds of code-gen for what one call does sub-second); **reasoning opacity** (harness loses visibility into what the sandbox discarded); mid-task reasoning needs don't batch (Anthropic's own tool-writing guidance); sandbox operational surface (limits, network policy, monitoring). Anthropic's τ²-bench negative result is the reminder that "obvious" wins sometimes invert on measured tasks (GLMC).

**Verdict for a 2–4-tool docs domain**: wrong default — below every threshold, no composition fan-out, no large intermediates. Right profile: sandbox-equipped harnesses doing multi-hop work (compare versions across libraries, batch-verify citations) or serving API-scale surfaces (100s–1000s of endpoints) — adopt as a **gated third adapter** ([benchmark-protocol.md](benchmark-protocol.md) gates; GLMC Finding 4, DSV §2).

## 4. Dynamic toolsets (the lazy middle)

Speakeasy's 3-meta-tool shape — `search_tools` (semantic **+ category overview** in the description, fixing "the model never thinks to search"), `describe_tools` (lazy schema load), `execute_tool` — captures most of the token win without code execution, at 2–3× calls and ~50% latency. Speakeasy's anti-Code-Mode argument (implementation cost) is its own position, not a measured head-to-head (DSV §3, GLMC Finding 3). Same shape as Context7's own 2-tool design at docs scale. Adjacent points on the same lazy-loading curve: Solo.io's MCP gateway **progressive disclosure** cut tokens −91% vs full schemas (vendor bench, KIMI §5), and FastMCP + TOON-style compact encodings reach **up to −98% on repetitive structured payloads** (community, KIMI §5) — both directionally consistent with the mechanism, both vendor/community-tier. An AWS-heroes piece calls code mode "the long-tail escape hatch, not the front door" (KIMI §2) — the same scenario-conditional reading this file reaches.

**Protocol-level lazy loading** (GEM §6): Anthropic's Tool Search Tool (`tool_search_tool_bm25_20251119` / `tool_search_tool_regex_20251119`) tags non-core tool definitions `defer_loading: true`, stripping them from the system-prompt prefix — only the ~500-token Tool Search Tool plus 3–5 primary non-deferred tools load upfront — and expanding matches inline at the end of the conversation as lightweight `tool_reference` blocks instead of mutating the static prefix. Because the prefix never changes, **prompt caching stays fully intact** while upfront tool context drops >85% (~77,000 → ~8,700 tokens on a 50+ tool setup). Tool-selection accuracy improved with the distracting schemas removed (Opus 4: 49%→74%; Opus 4.5: 79.5%→88.1%). This is the cache-aware version of the same loading-policy lever the whole file is about.

## 5. Decision matrix

Per deployment scenario — never averaged across studies (GPT2 §6.1, GLMP Ch.10, DSV §5.2, GLMC Finding 8):

| Scenario | Default candidate | Why | Non-negotiable controls |
|---|---|---|---|
| Coding agent with shell (Claude Code, Codex CLI, terminal mode) | **CLI + lean skill** | near-zero marginal schema; composability; local index works offline; *test, don't assume* — see gate below | bounded output (`--max-tokens`), JSON mode, stable exit codes; host allowlists to avoid safety-scan re-scans |
| GUI/remote client, no shell | **MCP, 2–4 tools, lazy shape** | structured calls; no shell dependency | small schema, bounded output, timeout/retry policy |
| Multi-user governed service | MCP **or** authenticated API | central identity/audit — deployment controls, not protocol magic | gateway auth, tenant isolation, quotas, audit logs |
| Offline / private docs | **local CLI + local index** | no egress, retention control, no metered API | encrypted local index, source ACLs, deletion workflow |
| API-scale surface (100s–1000s endpoints) | **server-side Code Mode or dynamic toolsets** | fixed init footprint; spec stays out of context; code filters before returning | sandbox contract ([security-licensing.md](security-licensing.md)) |
| Batch/CI codegen evals | **direct batch retrieval** (no tool loop) | CodeRAG-Bench evaluates via batch retrieval; per-call fees dominate at volume | — |
| IDE inline, sub-second | **prebuilt local index or hosted grounding API** | avoid tool-call round trips entirely; <10 tools load faster upfront | — |
| Small, stable doc set | lean in-repo **SKILL.md / llms.txt** | plausible lowest cost; adequacy unmeasured — check against gates | keep it lean (one measured 12.7k-token skill is a failure-mode illustration, n=1) |
| Long-tail breadth (100k+ libraries) | **federate to hosted indexes** (Context7, GitMCP, llms.txt) | crawl infrastructure is the cost; free supply keeps eroding | treat as fallback provider, never a hard dependency ([architecture.md](architecture.md)) |

**"CLI-first" means**: build and evaluate the retrieval core behind a shell-friendly interface first for the local developer scenario. It does not mean "CLI beats MCP everywhere" — no controlled docs-domain benchmark supports that (GPT2 §6.1, GLMC Finding 8), and the seven-scaffolding study above shows the interface is not even the dominant variable (DS §3). Two CLI taxes are real and unmeasured for docs: host safety-heuristic re-scans (mitigate with allowlists/hooks — measured cost for general CLIs is 1.3–2M Haiku tokens + 15 min per 30 runs, GEM §4) and verbosity (mitigate with bounded output). Neither mitigation has a measured cost for docs CLIs in any source (DSV §5). A field note from Svelte 4→5 breakages: rapid evolution near the model cutoff is exactly where live retrieval over a fresh index earns its keep — HN discussion frames MCP's "stop-gap" value as highest there (KIMI §6). Adjacent-field evidence that interface *labels* don't settle the question: SWE-agent's Agent-Computer Interface work and Terminal-Bench 4.0 (which now measures cost and tokens alongside resolution rate) both treat the interface as a design variable to sweep, not a winner to assume (GLMC Findings 3/8).

## 6. llms.txt: supply-side, not a retrieval fix

`llms.txt` solves *publishing* (agent-readable index + per-page markdown), not "which snippet answers this question" (DSV §4(g)). Supply is consolidating: Mintlify auto-generates llms.txt/llms-full.txt for every hosted site since Nov 2024 (with recursive `_llms` indexes and `.md` page endpoints — GLMC Finding 6), advertises them via HTTP Link headers, and ships per-site MCP servers (GLMP §7) — its newer stack also publishes an MCP server card, an agent card, and an agent-skills index so an agent that knows nothing about a site can discover everything it offers in one request (GLMP §7). Standalone generator tooling consolidated the opposite way: **Firecrawl deprecated its hosted llms.txt generator in mid-2025**, judging one-shot generation less valuable than platform-native publishing (GLMP §7). But adoption is partial — 0.2% of 1,500 crawled sites, **30% of which block AI bots outright**; major AI platforms largely ignore it; MDN does not publish it (GLMC Finding 6). Named adopters: Anthropic, Next.js, React, Mintlify publish it; X, Ping Identity, Fern (auto-generated), GitHub (as an API-style variant, whose maintainers report it useful mainly for multi-hop lookups — KIMI §3), and Bird (GEM §6) do too (GLMC Finding 6, KIMI §3). Quality variance is documented (Google Cloud: ADK's own llms.txt contained no links). HN debate is about incentives — who maintains the files (GLMP, GLMC). Tooling that treats it as ingest supply: `get-llms` (npm CLI — fetches llms.txt for all package.json deps to local disk), LangChain's `mcpdoc`, and Statespace (search engine over llms.txt docs exposed via web/SDK/MCP/**CLI**) (KIMI §3). A third supply-side pattern is the AI-generated digest — Cognition's DeepWiki turns repositories into navigable AI wikis (GLMP §7). **Use as an ingest source with graceful degradation to repo clones and HTML crawl; never as the strategy** ([architecture.md](architecture.md)). GEM §6 adds the v2 landscape (Jeremy Howard's standard; v2 updated Aug 2026; ~844,000 domains including Anthropic, OpenAI, Cloudflare, Stripe, and every Mintlify- or GitBook-hosted site): three machine-readable forms at the docs root — the curated `/llms.txt` index (H1 title, blockquote summary, operational guidelines, H2 link lists carrying per-page token counts), `/llms-full.txt` (one concatenated export excluding auto-generated OpenAPI/SDK dumps — the bulk-local-indexing feed), and per-page `.md` twins plus OpenAPI specs so API signatures never drift from implementation. The format has also fractured into marketing "GEO" files (zero observed retrieval benefit) versus genuine **agentic operating manuals** — an execution contract with intent-routing boundaries, canonical `.md` URL shapes, slug/version normalization rules, resolver workflows, per-link token budgets, and invariants/deprecations. Author only the latter.

Progressive-disclosure formalization (GLMP §7): Anthropic's Agent Skills (Oct 2025) is the cleanest statement of the contract — a skill is a folder whose YAML frontmatter (name + description, a few dozen tokens) is all that loads by default, with full instructions read only on task need; thousands of capabilities stay addressable at constant context cost. Its strategic signal compounded in Dec 2025 when Anthropic donated the Model Context Protocol to the neutral **Agentic AI Foundation** — protocol neutrality is the industry's stated direction, another reason a docs tool should treat MCP as one adapter among several ([architecture.md](architecture.md)).

Evidence it helps delivery: Mintlify's benchmark (full run retained 2,672 rows; 2,400 valid attempts, 20 sites, 4 serving arms) — linked llms.txt index reduced input tokens ~19–26% in the index-only contrast (41–60% in the combined HTML→md-link contrast), cut 404s near zero, and scored **≈94–99% accuracy conditional on valid attempts** (GPT1/GPT2 §4.4); inlining the whole index did not justify its token cost. Absolute pairs: HTML 296k vs md-link 175k (Claude) and 285k vs 115k (Codex) — percentages are within-agent only, never compared across agents (source's own warning); the index-only contrast is 215k→175k (≈19%, Claude) and 156k→115k (≈26%, Codex). Failure ledger: **272 excluded failed attempts — 256 Codex CLI crashes, 7 timeouts, 6 Claude network errors, 3 Claude contamination-gate failures** — the reason Mintlify reports valid-attempt-conditional accuracy and the cautionary example behind [benchmark-protocol.md](benchmark-protocol.md) Step 5 (GPT1/GPT2 §4.4).
